The problem, and the catch

One sentence says the option is gone.
The other tells you to use it.

What it checks

Claims your reference does not support

Invented interfaces

Commands, flags, environment variables, exit codes and endpoints that appear nowhere in your reference.

Features the reference denies

Options your source says were removed, are ignored, or never existed — offered to the reader as if they work.

Contradictions and misattribution

A default stated two ways, or a flag credited to the wrong command — useradd --system is right, your tool's isn't.

Two kinds of finding, never mixed

Contradicted by the reference means your source says the opposite, and the report shows you where. Not supported by the reference means something is simply absent — which may mean the draft invented it, or that your reference does not cover it, or that DocFacts misread it.

Collapsing those into one list would overstate the second and make the first easier to dismiss. So they get separate sections, and the weaker one says plainly that it is weaker.

  with:
    reference: docs/api-spec.md
    draft: docs/guide.md
    fail-on-findings: "false"

Run it on pull_request, never pull_request_target. Start non-blocking and watch what it says about your docs for a week before you let it fail a merge. Add --json to the CLI for machine-readable output.

Limitations

What it cannot do

This section is longer than the feature list, on purpose. A tool like this is only useful if you know where it stops.

A clean report does not mean your document is correct. It means nothing in it contradicted your reference in the specific ways listed above. There is no accuracy guarantee here and there will not be one.

Missing content isn't checked. Whether your guide covers what it needs to depends on what you need, which isn't in the reference. The largest gap.
Facts in prose aren't cross-checked. "Requires kernel 5.10" against a reference saying 5.15 will pass.
Nothing is executed, so nothing is validated. Whether the instructions work is not checked and cannot be.
Prose quality and ordering aren't checked.
Your reference is taken as true. A document faithful to a wrong reference passes.
Inference is heuristic. A reference formatted unusually may be read wrong — which is why the report prints what it inferred before any finding.

Tested by 2,577 automated tests and a run against six real documentation pairs from ESLint, Jest, Ruff, Prettier, Vitest and uv. That run found seven defects in DocFacts itself, six of which gave confident wrong answers. All are fixed and pinned by regression tests — and the synthetic test suite had found none of them, which is worth knowing when weighing any claim made from synthetic tests.

Privacy

Your documents never leave your machine

The documents you check are often an unreleased specification. A tool for reading those has no business opening a socket.

No network code at all

Not "we don't send much" — there is no HTTP client, no socket, no DNS lookup anywhere in the package.

No telemetry, no files written

No analytics, no crash reporting, no cache, no config file, no state directory. Nothing to opt out of.

Verify it yourself

A few files and no dependencies, so reading all of it is realistic. This should print nothing:

grep -rE "fetch\(|node:http|child_process" \
  package/dist/

That check runs as part of the test suite, so it keeps passing. The design is to be incapable rather than well-behaved.
